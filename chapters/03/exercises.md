# Chapter 03 | Exercises and knowledge checks

1. **Assumptions and trade-offs.** A stakeholder asks Atlas to treat `"case-1"` and `" case-1 "` as the same key. Identify the existing assumption that changes, propose a decision-maker and describe a compatibility risk. State whether normalisation applies to both new submissions and existing keys.

2. **Invariant and failing test.** Write an invariant stating that a rejected conflicting replay cannot alter existing state. Add a test that advances `R1`, attempts a conflicting replay and observes state through a valid replay. Introduce a defect that changes state before raising `ValueError`; verify that the new test fails, then remove the defect and verify that it passes.

3. **Laboratory extension, including all revision artefacts.** Propose Atlas **v1.2** and add `REQ-006`: a reviewer may not advance an unknown request ID. Record who has authority to approve that new obligation and agree an explicit expected error; the current model raises `KeyError`. Then make **all** of the following coordinated edits: (a) change `spec.json` to `version: "1.2"` and add the REQ-006 invariant with a named test; (b) expand `EXPECTED_IDS` in `atlas.py` to include REQ-006; (c) update the `validate_spec` hard-coded version check from `1.1` to `1.2`; (d) implement the chosen missing-ID behaviour and a `test_req006_...` that asserts it; (e) update the specification-version string in `capture.py` to `1.2` (ideally read it directly from `spec.json` instead); (f) update the traceability mapping and any acceptance-record heading or example that still claims v1.1; (g) run the suite, test both a valid link and a deliberately dangling test name, and retain the new `run-record.txt` with its hashes and actual exit status; (h) record external stakeholder policy approval separately. Explain why the new tests still do not prove real authentication, concurrent correctness or deployed-system security.
